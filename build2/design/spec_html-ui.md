## SUMMARY
I downloaded and measured every candidate geography source and proved an end-to-end, PowerShell-only build pipeline on this machine (there is NO node, NO npm, NO python, NO mapshaper here — `python3.exe` is the WindowsApps stub and fails). Recommended geography: world-atlas@2.0.2 `countries-110m.json` TopoJSON (107,761 B, ISC, Natural Earth public-domain source, 177 countries with `name` + numeric ISO id) for the world overview, and the OCHA COD-AB Ukraine boundaries from HDX (valid_on 2025-09-01, v05, CC BY-IGO) for ADM0/ADM1/ADM2 — critically, geoBoundaries gbOpen UKR ADM2 must be REJECTED because its `boundaryYearRepresented` is 2006 (495 pre-reform raions) whereas COD gives the correct post-2020 139 raions with official UA pcodes and bilingual EN/UK names; GADM must be rejected on licence. I wrote and debugged a Douglas-Peucker + quantise + delta-encode packer in PowerShell/C# (`pack.ps1`) and measured real outputs: ADM2 139 raions 611,152 vertices → 25,519 vertices → 159,891 B packed; ADM1 27 oblasts → 66,997 B; ADM0 → 20,394 B. Total embedded geography ≈ 355 KB, and a full realistic payload (geography + 5 km national posterior grid + 100 m robot-AO grid + 5,000 registered mines + app code) lands near 900 KB, about 5.6% of the 16 MB budget. Rendering should be Canvas2D + d3-geo from the single verified cdnjs bundle `https://cdnjs.cloudflare.com/ajax/libs/d3/7.9.0/d3.min.js` (279,703 B, confirmed to contain geoPath, geoNaturalEarth1, geoConicConformal, geoAzimuthalEqualArea, geoIdentity, geoGraticule, quadtree and d3-scale-chromatic) — deck.gl and Leaflet are both rejected, and deck.gl has no working cdnjs path at all. The decisive performance trick is to define the posterior grid in a projected CRS at build time so the heatmap is a true regular raster drawn with one `putImageData`+`drawImage` per frame, with an offscreen unique-colour pick canvas giving O(1) hit-testing instead of point-in-polygon over 139 raions.

### [verified] Proven simplification pipeline and exact resulting byte sizes
Algorithm: (1) normalise all Polygon geometries to MultiPolygon so nesting depth is constant; (2) drop sliver rings whose bbox max-extent < MinExt degrees; (3) Douglas-Peucker at tolerance Tol degrees via a C# Add-Type class; (4) round to 4 decimals for GeoJSON output, or quantise to a Q x Q integer grid over the layer bbox and delta-encode consecutive vertices for the packed output. Measured on COD ukr_admin2.geojson (139 raions, 611,152 input vertices): Tol=0.002/MinExt=0.01 -> 47,012 verts, GeoJSON@4dp 869,796 B, packed 260,513 B. Tol=0.005/MinExt=0.02 -> 25,519 verts, GeoJSON@4dp 486,304 B, packed 159,891 B. Tol=0.01/MinExt=0.03 -> 14,697 verts, GeoJSON@4dp 293,139 B, packed 106,115 B. COD ukr_admin1 (27 oblasts, 385,271 verts) at Tol=0.005/MinExt=0.02 -> 11,315 verts, GeoJSON@4dp 207,631 B, packed 66,997 B. COD ukr_admin0 at Tol=0.004/MinExt=0.02 -> 3,613 verts, GeoJSON@4dp 64,751 B, packed 20,394 B. The packed delta-int encoding is consistently ~3.0-3.3x smaller than 4-decimal GeoJSON. Runtime: 3.5 s for admin2, 2.0 s for admin1. Tol in degrees: 0.002 ~ 220 m, 0.005 ~ 550 m lat.

### [verified] Coordinate rounding alone (no vertex removal) is not enough
Regex-rounding geoBoundaries UKR_ADM2_simplified.geojson without removing any vertices: original 698,065 B -> 5dp 429,007 B -> 4dp 402,085 B -> 3dp 375,323 B. UKR_ADM1_simplified 761,290 B -> 4dp 587,325 B -> 3dp 533,857 B. Going from 4dp to 3dp buys only ~7% while degrading positions from ~11 m to ~111 m. Conclusion: rounding is worth doing (it is most of the win on raw COD data, which ships 15 decimals) but Douglas-Peucker vertex removal is what actually controls size. Use 4 decimals (~11 m) for GeoJSON output; 4 decimals is already finer than any Tol >= 0.002 deg (~220 m) justifies.
_source: PowerShell regex round + Get-Item .Length on each variant_

### [verified] Recommended geometry encoding: quantised delta-encoded integer rings
Format emitted by pack.ps1: {bbox:[minx,miny,maxx,maxy], q:6000, f:[{i:pcode, n:name_en, u:name_uk, p:parent_pcode, g:[[ [dx,dy,dx,dy,...] ...ring... ] ...polygon... ]}]}. Decode: x = minx + (cumsum dx) * (maxx-minx)/q, same for y. q=6000 over Ukraine's ~13.5 deg longitude span gives ~0.00225 deg (~170 m) quantisation, matched to a DP tolerance of 0.005 deg. Delta values are small integers so the JSON text is mostly 1-3 char tokens, which is why it beats 4dp GeoJSON by >3x. This is the same idea as TopoJSON quantisation minus arc-sharing; full TopoJSON arc deduplication would save perhaps another 40-45% on shared raion borders but requires topojson-server (node), which is unavailable here.
_source: Implemented and measured: packed 159,891 B vs GeoJSON@4dp 486,304 B for the same 25,519 vertices_

### [likely] Rendering recommendation: Canvas2D + d3-geo, two stacked canvases, pre-projected raster heatmap
Reject Leaflet-without-tiles: its Canvas renderer is per-feature (each grid cell would be an L.Rectangle with its own path op and its own event bookkeeping); 24,000+ cells makes pan unusable, and once you write a custom L.GridLayer you have written the canvas code anyway and gained only Leaflet's ~145 KB. Reject deck.gl: 1,245,822 B, no valid cdnjs path, requires WebGL — and in a sandboxed iframe or on a machine with a blocked/failed GL context it renders NOTHING, which for a landmine risk map is a dangerous failure mode rather than a degraded one. Recommend Canvas2D + d3-geo. Architecture: (A) offscreen 'base' canvas holding country/oblast/raion strokes drawn with d3.geoPath(projection, ctx), redrawn only on zoom-end, blitted each frame; (B) offscreen 'heat' canvas built from ImageData. The decisive trick: define the posterior grid in a PROJECTED CRS at build time so it is a regular raster in screen-affine space — use Lambert Azimuthal Equal Area centred 49N/31E (d3.geoAzimuthalEqualArea) for the national grid so cells have equal area and mines/km2 is honest, and UTM 36N (EPSG:32636) for the robot AO, since a 20 km AO sits inside one UTM zone. Then the heatmap redraw is ONE putImageData + ONE drawImage with ctx.imageSmoothingEnabled=false, i.e. O(1) per frame no matter whether the grid is 6,000 or 603,500 cells. Mines: cull with a d3.quadtree built once, draw only in-view points; above ~3,000 visible switch to aggregated count badges per raion. Hit-testing: do NOT run geoContains over 139 polygons on mousemove — render an offscreen 'pick' canvas where each raion is filled with a unique rgb(i>>16, (i>>8)&255, i&255) and read it with getImageData(x,y,1,1) for exact O(1) identification; re-render it only on zoom-end. Handle devicePixelRatio by sizing canvases to cssW*dpr and ctx.scale(dpr,dpr).
_source: reasoning, constrained by the verified bundle contents and the verified deck.gl/Leaflet sizes and 404s_

## PITFALLS
- Reaching for mapshaper, topojson-server, ndjson-cli or a Python geopandas script — none of them exist on this machine and `python3.exe` is a Store stub that silently errors. The whole build must be PowerShell + Add-Type.
- Using geoBoundaries UKR ADM2 because it is small and labelled 'Public Domain'. It is the 2006 495-raion system; Ukraine's July 2020 reform replaced 490 raions with 136. Every posterior aggregate would be keyed to administrative units that no longer exist and could not be joined to any modern UA dataset. (geoBoundaries UKR ADM1 is separately ODbL, not public domain.)
- The PowerShell array-unrolling trap that cost me a debugging cycle: `function Rings($g){ if($g.type -eq 'Polygon'){ ,@($g.coordinates) } else { $g.coordinates } }` and the equivalent `$plist = if(...){ @(,$x) } else {...}` BOTH unroll one level too far, so every Polygon feature gets iterated as individual coordinate pairs, every ring fails the `.Count -lt 4` guard, and the 109 Polygon features silently vanish leaving only the 30 MultiPolygons (I observed exactly feats=30). Fix: normalise all geometries to MultiPolygon up front with `$mp=New-Object System.Collections.ArrayList; [void]$mp.Add($f.geometry.coordinates); $f.geometry.coordinates=$mp.ToArray()`.
- Assuming d3 submodules are on cdnjs. https://cdnjs.cloudflare.com/ajax/libs/d3-geo/3.1.1/d3-geo.min.js is a 404, as are d3-scale-chromatic, topojson-client and deck.gl — the cdnjs metadata API returns 404 for all of them. Only the full `d3` bundle and the full `topojson` bundle exist there.
- Choosing deck.gl. Besides having no cdnjs path and weighing 1,245,822 B, it hard-requires WebGL; in a sandboxed iframe or with a lost GL context it draws nothing at all, and a blank landmine map is far more dangerous than a slow one.
- Drawing grid cells as individual fillRect or Leaflet L.Rectangle objects. At 24,000 cells this already stutters and at 150,000 it is unusable. The grid must be a raster blitted with a single drawImage, which requires the grid to be defined in the projected CRS at build time — retrofitting that later means regenerating all the posterior data.
- Building the national grid in raw lat/lon degrees. Cell ground area shrinks markedly from southern to northern Ukraine, so mines/km2 would be systematically wrong; use an equal-area projection for the grid definition.
- Letting prefers-color-scheme change the heatmap ramp. The same hex must always mean the same number — if the OS theme silently re-encodes the data, two people screenshotting the same district get contradictory-looking maps.
- Using viridis or any ramp whose low end is near-black on a dark ground: 'lowest risk' becomes indistinguishable from 'no data / not modelled', which is exactly the confusion that gets someone killed. Clip the ramp and give 'no data' a hatch.
- Using green for the low class, or any word from the safe/clear/OK family in a legend label. Users read green as permission no matter what the legend text says, and a single 'Low risk' string can be screenshotted and passed around as clearance.
- Thinning or clustering away CONFIRMED mine markers for performance without saying so. If dots must be aggregated, show an explicit per-region count badge — never silently drop a confirmed hazard record.
- Showing a posterior mean without its credible interval, or showing '+/- SD' for a count that is bounded below at zero and heavily skewed. Use equal-tailed 5th/95th percentiles and render them as an interval bar.
- Rounding coordinates to 3 decimals hoping for size savings: it buys only ~7% over 4 decimals (375,323 vs 402,085 B in my test) while degrading positions from ~11 m to ~111 m. Vertex removal, not decimal truncation, is what controls file size.
- Forgetting devicePixelRatio on the canvases — the heatmap raster and the hairline raion strokes both look wrong on a HiDPI screen, and the pick-canvas hit test will be offset by a factor of dpr if only some canvases are scaled.
- Downloading the full 84 MB HDX zip at page-build time in CI without caching it; and note ukr_admin3/admin4 (60 MB / 144 MB) are hromada/settlement level — do not embed them, they are far beyond what the budget or the UI needs.
