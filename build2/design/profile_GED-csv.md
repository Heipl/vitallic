### [verified] Parser performance and the working RFC4180 approach
Inline-C# char-by-char state machine over a StreamReader with a 1 MB char buffer processes the whole 250 MB / 385,918-row file in 0.96-1.83 s depending on how much it aggregates. Critical implementation details: (a) read into char[] and refill on demand rather than ReadLine, because fields contain newlines; (b) inside a quoted field, on seeing '"' peek the NEXT char - refilling the buffer first if the peek would cross a buffer boundary - and treat '""' as a literal quote, otherwise close the quote; (c) treat '\r' outside quotes as skippable so CRLF and LF both work; (d) strip a possible '﻿' BOM from the first header name. Scripts: profile_ged.ps1 (pass 1: counts, distributions, cells), profile_ged2.ps1 (pass 2: dates, adm coverage, payload sizing), profile_ged3.ps1 (pass 3: centroid pile-up). One C# compile gotcha hit and fixed: 'double la,lo;' passed to TryParse in a short-circuited && is flagged CS0165 'use of unassigned local variable' - initialize to 0 and split the two TryParse calls.
_source: Ran all three scripts; PARSE_SECONDS printed 1.83, 1.67 and 0.96; fixed the CS0165 compile error by initializing la/lo._

## RECOMMENDATIONS
- Parse date_start/date_end with the format string "yyyy-MM-dd HH:mm:ss.fff" (or take s.Substring(0,10)). The bare "yyyy-MM-dd" exact-parse fails on 100% of the 385,918 rows.
- FILTER OR DOWNWEIGHT BY where_prec BEFORE BUILDING THE PRIOR. Build the Ukraine fine-resolution prior from where_prec<=2 (24,079 events, 76.3% of Ukraine) or where_prec<=3 (25,390 events, 80.5%). Never feed where_prec 4/5/6/7 into a fine grid as point masses - they are administrative centroids, not event locations.
- Explicitly drop or spatially redistribute the 1,194 Ukraine events at exactly (49.000000, 32.000000). They are where_prec=6 country-centroid records and carry 89,634 deaths = 36.6% of Ukraine's entire fatality total. Left in, they produce a giant phantom minefield near Cherkasy, one of the least-affected parts of the country.
- If you want to keep the fatality mass from where_prec 4/5/6 events, redistribute it across the relevant admin unit (or, for wp=6, across the wp<=2 spatial density) instead of leaving it as a delta function. wp>=4 carries 107,451 of Ukraine's 245,068 deaths (43.8%), so discarding it outright loses real signal.
- Model where_prec as the spatial kernel bandwidth rather than a hard filter: wp=1 -> sigma ~0-2 km, wp=2 -> sigma ~25 km (the codebook's explicit radius), wp=3 -> raion extent, wp=4 -> oblast extent. This is the principled way to convert geocoding precision into prior uncertainty.
- Merge 'Kyiv Special Republican city' (58 events, best 537) and 'Kiev Special Republican city' (6 events, best 88) into one ADM1 unit before any district-level join, or the Kyiv tile will be split and both halves will render wrong. Do NOT merge 'Kyiv oblast' (255 events) into the city - it is a separate unit.
- Key all admin joins on the (country, adm_1) PAIR, never on adm_1 alone: 1,682 distinct adm_1 strings vs 1,711 distinct country||adm_1 pairs means names are reused across countries.
- Store the Ukraine 0.01-deg grid SPARSE. Only 2,347 of 1,366,058 bbox cells are occupied (0.172%); a dense array would be 1.4M entries for nothing. A sparse [r,c,n] list is ~54 KB.
- Embed both layers with confidence: Ukraine 0.25-deg cells ~6.4 KB, Ukraine 0.10-deg ~17.9 KB, Ukraine exact points ~54 KB, global 0.25-deg overview ~215 KB. Total well under 300 KB, so the entire remaining 16 MB budget is available for embedded oblast/raion GeoJSON boundaries (simplify with Douglas-Peucker and 4-dp coordinates).
- Deduplicate on exact coordinate strings before emitting points: 385,918 global events collapse to 56,232 unique lat/lon points (6.9x), and Ukraine's 31,547 events collapse to 2,442 unique points (12.9x). Emit unique points with an event count, not one entry per event.
- Use adm_1 for the district heatmap in Ukraine (27 distinct oblast strings, 26 after the Kyiv merge, covering essentially the whole country) rather than adm_2, which has 172 distinct values in Ukraine and is empty on 18.1% of rows globally.
- Decide deliberately between event-count and fatality-weighted priors and expose the choice in the UI. Rwanda is #1 by sum(best) at 794,117 but only #28 by event count at 2,604; Ukraine is #3 by events and #5 by fatalities. For landmine risk, event count and duration of frontline presence are likely better proxies than fatality count.
- Weight recent years heavily for Ukraine: 27,979 of 31,547 Ukraine events (88.7%) fall in 2022-2024, and the 2014-2021 frontline (Donetsk/Luhansk contact line) is spatially distinct from the 2022+ front. Do not pool all years into one flat prior.
- Reuse the working RFC4180 C# parser at C:\Users\rinoa\AppData\Local\Temp\claude\c--Users-rinoa\cdbe3cc9-ee66-4c79-a765-8d489a4e0a51\scratchpad\profile_ged.ps1 for the actual build step - it handles this file correctly in under 2 seconds and is already cross-verified against TextFieldParser.
- Do not use where_prec=7 as 'country-level' - that is where_prec=6. Level 7 means international waters/airspace, has only 251 rows globally and 10 in Ukraine, and should be dropped entirely for a landmine model.
- For the robot's fine local grid, note that Ukraine has only 2,347 occupied 0.01-deg cells (~1.1 km cells) - that is far coarser than a robot sweep. The GED prior can only realistically seed a ~1-25 km resolution risk surface; anything finer must come from the robot's own posterior updates.

## PITFALLS
- Splitting on newline gives 463,622 lines but there are only 385,918 records - a naive line split over-counts by 77,704 and corrupts every field after an embedded newline. The source_article field routinely contains quoted, comma-and-newline-laden text.
- Assuming where_prec=7 means 'country-level'. It does not: 6 is country-level, 7 is international waters/airspace. The task brief states this incorrectly.
- Parsing date_start with "yyyy-MM-dd". It is 23 chars, 'yyyy-MM-dd HH:mm:ss.fff'. A strict TryParseExact on "yyyy-MM-dd" returns false for every single row and silently yields zero valid dates (this exact failure happened in pass 1: date_start_parsed=0, date_start_min=null).
- Treating all 31,547 Ukraine coordinates as real event locations. 7,157 of them (22.7%, where_prec>=4) are administrative or country centroids, and they are the highest-fatality points in the dataset, so they dominate any fatality-weighted kernel.
- Trusting lat/lon completeness as a proxy for lat/lon quality. Zero rows are missing coordinates, which makes it tempting to skip validation entirely, but where_prec is the real quality signal and it is ignored by default.
- Building a dense 0.01-deg raster over the Ukraine bbox: 1,366,058 cells of which 2,347 are occupied. Dense storage or a dense JS loop will blow the file size and the render budget for a 0.17%-full grid.
- Merging Kyiv on the string 'Kyiv' only - the dataset contains BOTH 'Kyiv Special Republican city' and 'Kiev Special Republican city' as separate adm_1 values, plus a separate 'Kyiv oblast' which is a different administrative unit and must NOT be merged into the city.
- Joining on adm_1 alone across countries: 1,682 distinct adm_1 strings vs 1,711 country||adm_1 pairs means some names are shared between countries and will cross-contaminate.
- Assuming Ukraine data goes back before 2014 - it does not. year_min for Ukraine is 2014 and events_2014_plus equals the full 31,547. Any 'pre-war baseline' from GED for Ukraine will be empty.
- Expecting WebFetch to read a codebook PDF. It returns an apology for binary content; the PDF must be inflated locally (pdftext.ps1 does this in pure .NET).
- In inline C#, writing `double la,lo; bool ok = TryParse(...,out la) && TryParse(...,out lo);` fails to compile with CS0165 'use of unassigned local variable' because of short-circuiting. Initialize both to 0 and split the calls.
- Forgetting to refill the char buffer before peeking the character after a '"' inside a quoted field. If the escaped-quote pair straddles a 1 MB buffer boundary the parser will silently mis-close the quote and shift every subsequent field by one for the rest of the file.
- Ignoring that 30,021 rows (7.8%) have best=0 and 143,147 (37.1%) have best=1. A fatality-weighted prior discards or near-discards 45% of all events; an event-count prior does not.
